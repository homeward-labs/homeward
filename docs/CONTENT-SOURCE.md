# 服务端内容源：为什么它优先级最高

> 配套：部署形态见 [DEPLOYMENT.md](./DEPLOYMENT.md) · 架构见 [ARCHITECTURE.md](./ARCHITECTURE.md)
> 实现：`src/knowledge_base/updater.py`（知识库更新器）、`src/license/verify.py`（许可离线验签）

---

## 一句话

**家卫的客户端是「薄客户端」：所有观测都在本地算、本地存；它唯一向外要的东西，是「内容」和「信任根」。**

所以这里的「服务器」**不是云端后台**，而是**内容分发源 + 信任根**。它不跑业务进程、不存用户数据、不做账号体系 ——
它只负责把「谁是谁」（域名归属知识库）和「谁说了算」（许可公钥 / 构件分发清单）以可校验的静态文件发出来。

---

## 薄客户端三原则

| # | 原则 | 落到代码里是 |
|---|---|---|
| 1 | **数据不出户** | 观测结果、设备清单、动作登记只落本地 SQLite（`src/adapters/sqlite_registry.py`）；**零遥测** |
| 2 | **内容向外取** | 域名归属库、行为模式库、ASN 表从内容源下载（`KnowledgeBaseUpdater`） |
| 3 | **信任本地验** | 许可用 Ed25519 **离线验签**，校验不依赖我方服务器是否存活（`src/license/verify.py`） |

客户端刻意**不存放、不展示**知识库全文与服务端内部数据 —— 这是隐私工具的自我要求，也决定了：
**内容只能从服务端来，服务端缺失就直接封顶客户端的能力上限。**

---

## 服务端做什么 / 绝不做什么

| ✅ 服务端做 | ❌ 服务端绝不做 |
|---|---|
| 静态托管知识库文件（`domains.csv` / `behaviors.json` / `asn.csv`） | 接收任何观测数据、设备清单、家庭拓扑 |
| 发布 `VERSION` + `CHECKSUM` + 签名，供客户端校验 | 做账号体系、做登录、做用户画像 |
| 承载知识库众包回路（Issue / PR → 合并即发新版） | 做云端分析、把判定搬到云上 |
| 提供许可信任根（公钥随构件注入，见 `docker/Dockerfile` 的 `HOMEWARD_LICENSE_PUBLIC_KEY_B64`） | 追踪设备激活、回传激活心跳 |
| 发布构件分发清单（镜像 / 原生包 / 闭源组件） | 静默上报 —— 任何形式都不行 |

> **红线（写死，不接受例外）**：家卫是隐私工具，**自身必须零遥测**。
> 更新器里曾放过 `submit_anonymous_data()` 这类方法，会把家里的域名与行为摘要发往远端 —— 与产品定位根本冲突，已移除。
> 将来若做社区共建，必须同时满足：**默认关闭 + UI 显式开关 + 逐条用户确认 + README 明示**，绝不埋在更新器里静默上报。

## 内容源清单与降级语义

| 文件 | 用途 | 缺失 / 校验失败时客户端怎么做 |
|---|---|---|
| `VERSION` | 版本号，决定是否更新 | 取不到就**跳过本轮**，保持原库，绝不猜测 |
| `domains.csv` | 域名 → 组织归属（**必需**） | 必需文件缺一 → **整包放弃**（见下） |
| `behaviors.json` | 行为特征签名（**必需**） | 同上 |
| `asn.csv` | ASN / 注册机构（可选） | 下载失败只**跳过该文件**，不阻塞本轮 |
| `CHECKSUM` | sha256 校验 | 不匹配 → 整包放弃；文件不存在 → 跳过校验 |

三条已实现的不变量（都是踩过坑后固化下来的）：

1. **版本号按数值逐段比较**，不是字符串比较 —— 字符串世界里 `'10.0.0' <= '9.0.0'` 成立，
   会导致知识库永远被判成「已是最新」从此不再更新。见 `updater._version_key()`。
2. **全或无替换**：先下到临时目录，必需文件齐了才原子替换。早期「逐个下载、失败就 continue」
   会留下「新版域名库 + 旧版行为库」的错配，而版本号根本表达不了这种半新半旧。
3. **失败即保持原状**：网络抖一下不会把用户的知识库搞坏，最坏情况是「没更新」。

## 为什么服务端优先级要高于「客户端新功能」和「打包渠道」

1. **它是唯一「改一次、全网生效」的地方。** 客户端改动要等用户拉新镜像 / 升级包才生效；
   服务端改一行知识库，所有在线客户端下一轮就拿到。
2. **它是当前最大的能力缺口。** 首发知识库仅 143 行，且默认内容源仓库尚未创建 —— 更新链路目前是 404，
   客户端知识库会永远停在首发版。**这条链路不通，客户端做得再漂亮也只是静态快照。**
3. **它是众包回路的入口。** 用户提交「某个域名归谁」→ PR 合并 → 自动成为新版本 → 全网下发。
   知识库能不能滚雪球，取决于这条回路，而不是取决于客户端 UI。
4. **客户端刻意不存放、不展示**，所以服务端是内容唯一出口，优先级天然更高。
5. **它的成本最低。** 静态文件 + `VERSION` + `CHECKSUM` + 签名即可，不需要服务器进程、不需要数据库、
   不需要运维。用最小形态换最大杠杆。

## 落地顺序建议（技术侧）

| 优先级 | 事项 | 说明 |
|---|---|---|
| **P0** | **内容源仓库**（`homeward-labs/knowledge-base`） | 数据文件 + `VERSION` + `CHECKSUM` + 签名 + 众包 Issue/PR 模板 + 自动生成校验和的 CI |
| **P1** | 客户端消费侧加固 | 可配置源地址、签名校验（不只 checksum）、更新失败在 UI 上可见（不静默） |
| **P2** | 分发渠道 | iStoreOS 商店包 `.ipk` / GHCR 预构建镜像 / 飞牛 `.fpk` |

> **注意**：提高服务端优先级 ≠ 把家卫云端化。
> 服务端永远只是**静态内容源与信任根**；判定、存储、展示全部留在用户自己掌控的那台设备上。
> 这是家卫对用户的核心承诺，不因任何便利性理由让渡。
